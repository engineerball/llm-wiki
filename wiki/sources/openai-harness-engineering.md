# Harness Engineering - Leveraging Codex in an Agent-First World

**Source:** OpenAI Engineering Blog, February 2026
**URL:** https://openai.com/index/harness-engineering/

## Summary

OpenAI's internal team built a ~1-million-line software product in 5 months using [[Codex]] agents with zero manually-written code. The experiment showed that the primary engineering challenge shifts from writing code to designing the environments, feedback loops, and scaffolding that let AI agents work reliably — what OpenAI calls [[Harness Engineering]].

## Key Metrics

- ~1,000,000 lines of code generated
- ~1,500 pull requests merged
- 3.5 PRs per engineer per day
- Team size: 3 → 7 engineers
- Estimated 10x speedup vs traditional development
- First commit: late August 2025; delivery: 5 months later

## Core Thesis

> "The discipline shows up more in the scaffolding rather than the code."

Engineers shifted from writing code to:
- Breaking complex goals into agent-legible building blocks
- Creating missing tools and abstractions
- Designing environments, specifying intent, building feedback loops

The harness is the full environment surrounding an agent: repository structure, CI configuration, formatting rules, package managers, application frameworks, project instructions, external tool integration, and linters.

## Lesson 1 — Repository as Knowledge System

The initial "giant AGENTS.md" approach failed: a large instruction file crowds out the task, the code, and the relevant docs — the agent optimizes for the wrong constraints.

Solution: **progressive disclosure**
- AGENTS.md as a lightweight table of contents (~100 lines)
- Structured `docs/` directory containing architecture maps, design docs, product specs, auto-generated references
- Mechanical linting to maintain freshness and cross-links

Key principle: **"If the agent can't see it, it doesn't exist."** All critical knowledge must live in the repository as readable markdown.

## Lesson 2 — Architectural Constraints Enable Speed

Strict layered dependency model enforced from the start:

**Types → Config → Repo → Service → Runtime → UI**

Cross-cutting concerns (auth, telemetry, feature flags) enter only through explicit Provider interfaces. Dependencies validated mechanically via custom linters.

This centralized architectural control — typically introduced at enterprise scale — became a prerequisite for autonomous agent development. It prevents code degradation at high throughput.

## Lesson 3 — Agent Visibility into Runtime State

Codex was wired into:
- Chrome DevTools Protocol for UI validation
- Observability stacks (logs, metrics, traces) via LogQL/PromQL
- Per-worktree isolated app instances
- Agents ran single tasks continuously for 6+ hours

End-to-end agent capability per feature:
1. Verify codebase state
2. Reproduce bug (generate diagnostic video)
3. Implement fix
4. Boot app instance, verify UI behavior
5. Access ephemeral observability stack
6. Open pull request, respond to review feedback
7. Detect and remediate build failures
8. Escalate only when human judgment needed
9. Execute merge

## Lesson 4 — Merge Philosophy

Traditional blocking gates became counterproductive at agent throughput:
- Minimal blocking merge gates
- Short-lived pull requests
- Test flakes resolved via follow-up runs (not blocking)
- Corrections cheaper than indefinite waiting

## Lesson 5 — Entropy Management

Pattern drift addressed through "golden principles" encoded directly in the repository:
- Centralized shared utilities over ad-hoc helpers
- Enforced type safety at boundaries
- Background Codex tasks scanning for deviations, auto-generating targeted refactoring PRs
- Technical debt treated like compound interest — addressed continuously

## Lesson 6 — Boring Technology Wins

"Boring" (well-established) technology outperformed novel libraries because:
- Better compositional stability
- Richer training data representation for the model
- Simpler agent modeling

In some cases, reimplementing functionality rather than importing libraries gave better outcomes — full observability integration and comprehensive test coverage.

## Initial Scaffold

Repository scaffold generated by Codex CLI using GPT-5, guided by a small set of existing templates. This included repository structure, CI configuration, formatting rules, and application framework selection.

## Remaining Open Questions

- Long-term architectural coherence over years
- Where human judgment provides maximum leverage
- How the system evolves as models improve
- Generalization to other repository structures
